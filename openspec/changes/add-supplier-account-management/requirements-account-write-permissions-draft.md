# 供应商账号分级配置权限：需求草案

状态：待产品确认，**尚未作为实施规范**

日期：2026-09-24

关联变更：`add-supplier-account-management`

## 1. 背景和目标

目前供应商创建表单/API 对所有供应商使用同一组有限配置字段；`review_required` 只影响创建后是否自动通过，并不决定供应商可以填写哪些字段。另一方面，管理员「供应商管理 → 供应账号 → 查看配置」只能编辑部分基础配置，不能覆盖「账号管理」编辑界面的全部账号参数。结果是：受审核供应商填写了不应决定的运行参数，免审供应商却无法把可用账号配置完整。

目标是**继续使用现有的 `review_required` 设置**，按当前供应商权限决定网页表单和系统令牌 API 能提交的字段。创建、批量导入、更新及系统令牌页的示例保持同一套后端规则；供应商页面不解释“可信/不可信”或设置缘由，只显示当前可填写、可调用的请求体。

## 2. 权限边界

| 项目 | 需要审核：`review_required=true` | 无需审核：`review_required=false` |
|---|---|---|
| 账号身份 | 允许 `name`，以及用于识别凭据类型的 `platform` / `type`；`external_id` 建议仅作为可选去重标识 | 同左，另可填写备注等账号基础资料 |
| 凭据 | 仅允许当前账号类型完成提交所必需的邮箱、网页登录密码、Key/Token 等凭据；不允许模型映射或调度配置 | 允许该 `platform + type` 在管理员账号编辑界面支持的账号凭据及非敏感配置，按类型逐项校验 |
| 代理与网络 | 供应商不选择代理、不能提交代理地址或代理 ID；代理由平台策略确定，管理员审核时可调整。具体生成规则见第 7 节待确认事项 | 可选平台库存内启用、未过期的代理；仍不能输入自定义代理地址或代理凭据 |
| 运行和模型 | 不允许备注、并发、优先级、负载因子、到期时间、模型白名单/映射、请求协议、流式选项、配额限制、额度/计费配置及其他高级参数 | 可配置适用该账号类型的账号管理参数，包括上述设置；使用服务端允许字段清单，而非直接接受任意 `credentials` / `extra` JSON |
| 分组与状态 | 无权指定分组、开启状态或可调度状态；提交后固定 `pending + disabled + schedulable=false` | 创建时自动审核；允许在管理员明确授权的同平台分组范围内配置或采用预设分组，可主动停用/恢复已通过账号；不可修改审核结果或直接写 `schedulable` |
| 审核 | 管理员填写完整配置、测试并单独审核通过后，才进入分组和客户流量 | 同平台预设分组、库存代理和所有配置校验成功后才可创建并投入调度；缺失前置配置必须拒绝，不可降级为无分组可用 |

供应商始终不能写入 `supplier_id`、`review_status`、`reviewed_by`、系统运行态、代理凭据、影子/Composite 结构、其他供应商资源、任意请求头覆盖或不受控的上游 URL。账号归属来自 JWT/系统令牌；允许的平台和认证类型仍受管理员配置的 `allowed_account_kinds` 约束。敏感凭据单向提交、加密/脱敏保存，不从列表、详情、审核页面或文档示例回显真值。

### 不同类型的最小凭据例外

“邮箱、密码、Key”是普通账号的业务描述，**不能直接作为所有类型唯一的 JSON 字段清单**：

- API Key / Upstream：`credentials.api_key`；某些 `upstream` / Antigravity API Key 还必须有经平台校验的 `base_url`，否则不能连接上游。
- OAuth / Setup Token：现有契约要求 `email`、`password`、`access_token`，可能还需 `refresh_token` 等维持可用性的令牌；供应商现有授权/换票入口继续可用，不能要求管理员凭空补齐供应商隐藏 Token。
- Bedrock、Service Account、国内平台和 OpenCodeGo：现有必需的密钥、地区、认证模式、账户模式或协议字段不完全等同于 `api_key`。建议仅保留连接身份的必需字段，其余由平台默认值或管理员审核时设置；无法在不让供应商配置额外字段的前提下提交的类型，必须明确禁止该权限下提交并给出原因，不接受无效半成品。

每个 `platform + type` 都需列出受审核、免审核各自的必填字段、可选字段、默认值及校验规则；不能仅以“隐藏前端输入框”作为权限控制。

## 3. 管理员审核与配置

管理员在「供应商管理 → 供应账号」中打开账号后，应能配置与「账号管理 → 编辑账号」**适用于该平台和认证类型的全部账号级选项**，包括基本信息、库存代理、模型/协议与连接参数、并发和优先级、负载因子、计费倍率、过期/停调设置及适用的平台高级配置。应复用现有字段定义和校验逻辑，避免两个页面长期出现不同结果。

供应商提交的 Key、Token、网页登录密码等敏感字段仅显示“已提供”，不得由管理员完整编辑表单回填、覆写或意外清空；现有单独的密码查看流程不等于允许编辑供应商 Token。管理员保存配置不自动批准；待审核账号依然不可调度。管理员完成必要配置后可以调用现有测试能力，**在最后一次影响连接的修改之后重新测试**，再单独选择有效分组并审核通过。审核通过使账号进入所选分组并可能立即服务客户，确认动作须明确提示这一后果。测试是否为硬性通过门槛见第 7 节。

## 4. 供应商网页和 API

- 供应商新增、编辑、JSON/CSV/逐行批量导入按**请求发生时**的 `review_required` 和 `platform + type` 动态展示/解析有效字段。切换权限后刷新页面即可得到新字段；旧页面提交的超权字段仍由后端拒绝。
- 继续使用 `POST /api/v1/supplier/accounts`、`POST /api/v1/supplier/accounts/batch`、`PUT /api/v1/supplier/accounts/:id`；JWT 与系统令牌调用同一权限检查。无需为两种权限新增两个可绕过的创建接口。
- 受审核模式下的请求体仅接收必需身份和凭据字段；`proxy_id`、`concurrency`、`priority`、`load_factor`、`notes`、`extra`、`group_ids`、`status` 等越权字段明确返回 422，指出字段路径，不静默丢弃。批量导入逐项报告哪一行、哪个字段不被允许；仍保留现有幂等约束。
- 免审核模式下，外层账号参数、各平台 `credentials` 子字段及适用的高级配置由后端白名单逐项验证；上游 URL 仍须通过域名/SSRF 检查。不得把管理员通用 `PUT /admin/accounts/:id` 直接开放给供应商。
- 更新也按当前权限判断，而不仅是创建。权限从免审核改为需要审核后，供应商不能再修改高级设置；此时修改凭据要重新进入待审核并停止调度。权限从需要审核改为免审核时，已有待审核/驳回账号不因策略切换而自动获批，历史已通过账号也不追溯改写。
- 受审核模式可主动停止自己**已审核**的账号；不能通过更新恢复待审核/驳回账号。免审核模式仅可在其已通过且绑定合法分组、代理时恢复，不允许把审核状态和运行状态混用。

## 5. 系统令牌页面的接口文档

原位置沿用 `SupplierAccessTokenView` 内的 `SupplierApiGuide`。页面从当前供应商资料读取权限，不显示“信任供应商”“无需审核”等策略解释；仅呈现**此刻可使用**的字段清单、必填提示、类型选择、创建/批量/更新示例和预期返回结果。权限变化后，两套文档模板自动切换，复制的 cURL/PowerShell 示例必须能对应当前实际可接受的请求体。

文档必须包含：认证头 `x-api-key`、幂等头、当前可选代理规则、按账号类型的凭据示例、允许/禁止的字段、422 字段错误、更新后是否会待审核、敏感字段不回显、测试与审核是不同操作。不展示真实系统令牌或已有账号密钥。后端 `/supplier/me` 现已返回 `review_required`，前端可据此选择文档模板；字段权限仍由后端权威校验。

## 6. 验收场景

1. 管理员保持默认需要审核；供应商网页、令牌 API 和批量导入只接受当前类型的最小账号身份及凭据。伪造高级字段一律拒绝，记录无部分生效；账号待审核且客户不可用。
2. 管理员能在审核页配置该账号的全部适用管理参数；保存后仍为待审核，测试不会隐式审核；通过审核时必须有有效库存代理和合法分组，才允许进入客户流量。
3. 管理员为供应商启用免审核并配置合法默认分组；供应商网页和 API 可设置其账号类型适用的完整参数；创建、更新经校验后按设置运行，不越权访问其他租户或管理接口。
4. 缺少库存代理、无有效分组、危险上游地址、字段类型错误、越权 `extra`/`credentials` 子键和跨租户账号均明确失败；密码、Key/Token 不进入普通响应、示例、审计明文。
5. 双向切换审核设置后，既有账号状态不自动变化；新请求立即应用新字段权限。受审核模式下更新已启用账号的凭据必须重新停用待审。
6. 系统令牌页面始终展示与当前权限一致且可以复制执行的请求示例；不会展示另一套当前不可调用的参数。

## 7. 待确认（实施前需定案）

1. **受审核账号的代理如何绑定？** 现行系统要求上传及 OAuth 授权时都有有效库存 `proxy_id`，代理本身没有“所属平台”字段。如果供应商完全不能选择代理，建议新增管理员为供应商/平台指定的默认库存代理，由服务器自动绑定；未配置或失效则拒绝提交/授权。是否采用此方案？
2. **复杂认证类型如何处理？** 对必须提交 `base_url`、AWS/Service Account 配置或国内平台模式的账号，建议仅放开连接必需的类型专有字段，其余锁定；如果必须严格只有名称、邮箱/密码、Key，则这些类型在受审核权限下暂不可提交。选择哪种？
3. **免审供应商的分组、倍率和运行开关范围？** 建议允许分组选择但仅限管理员预先授权的同平台分组；允许账号级计费倍率但限定后端范围；允许主动停用/恢复已通过账号，绝不允许写审核状态或直接写 `schedulable`。是否需要连分组和计费倍率也由管理员独占？
4. **审核测试是否为硬性门槛？** 目前测试是管理员可执行但不强制成功；建议可先维持人工确认，若要求“最后一次配置变更后测试成功才可通过”，须持久记录测试结果和配置版本，避免只在前端提示产生伪安全感。

确认上述决策后，再更新原 `design.md`、凭据契约、规格和实施任务；本草案暂不改变当前接口行为。
